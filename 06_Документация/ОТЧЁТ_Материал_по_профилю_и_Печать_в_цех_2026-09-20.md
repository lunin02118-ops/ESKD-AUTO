**Главное: сегодня надстройка не смотрит на геометрию детали вообще.** Она не обходит дерево построения,

переносит из детали в свойства, но никогда не сверяет его с тем, из чего деталь сделана.

Косвенные признаки геометрии в коде уже есть, но в другом месте и для другой цели:

* список вырезов читается только ради длины и количества — `Sw\LzkService.cs:479-504`;
* **материал тела не читается нигде.**

Канал для замечаний, который нужен по задаче, уже работает и не требует модальных окон:
`SyncReport.Warnings` → `StatusLine()` → задача `status`, выполняемая в простое.

## 3. Откуда брать сечение и толщину — проверено на живых деталях

**Свойства профиля доходят до детали сами.** Открыты настоящие детали изделия NC3-7R: в папке списка
вырезов лежат ровно те свойства, что записаны в файле профиля:

```
Description   = Труба 40х20х1,5 ГОСТ 8645-68
Сортамент     = Труба прямоугольная 40х20х1,5 ГОСТ 8645-68
Наименование  = Труба прямоугольная
```

Читаются они обычным чтением свойств папки списка вырезов — **без отката модели и без открытия файла

у детали `NC3-7R.02.003 Закладная высоты` даёт 3,000 мм при материале «Лист 3,0» — сходится.

**Запасной источник — путь к файлу профиля** (`WeldmentProfilePath`). Но с оговоркой, см. П-6.

### Исправление к первой редакции

В `ТЗ-02_…:402` записано, что имя профиля через API получить не удаётся. Это неверно: свойство называется
`WeldmentProfilePath`, а конфигурация — `ConfigurationName`.

При этом **`ConfigurationName` на всех проверенных деталях оказался пустым** — и на боевых, и на
построенных через API. Пустое значение означает, что берётся активная конфигурация файла профиля.
Значит **опираться на имя конфигурации нельзя**, источник — свойства и путь.

## 4. Чего делать нельзя

**Откат модели.** Чтение выборок через `AccessSelections` откатывает модель по дереву построения, а в
откаченном состоянии материал телу назначить нельзя — API возвращает отдельную ошибку. Нужды в нём нет:
всё необходимое читается без отката.

**Назначение материала детали целиком.** Для сварной детали это перетирает материалы тел, то есть рушит
раскладку по позициям списка вырезов. Материал тела перекрывает материал детали — это штатный механизм.

**Назначение материала прямо в обработчике сохранения.** Только отложенно, в очереди простоя
(`PendingIdleTasks`, сделан при разборе R01).

Практическая деталь: `IPartDoc.SetMaterialPropertyName2` **не возвращает ничего** — при неверном имени
материала молча ничего не делает. `IBody2.SetMaterialProperty` возвращает честный код ошибки. Поэтому
назначать надо по телам.

## 5. Предлагаемый алгоритм

При сохранении детали (только чтение):

```
если деталь — сварная конструкция:
    для каждой папки списка вырезов:
        типоразмер := свойство «Типоразмер» (запасной путь — «Сортамент» или путь к профилю)
        ожидаемый материал := поиск в библиотеке по «Типоразмер»
        текущий материал := материал тел этой папки
        если ожидаемый не найден → замечание «не удалось найти в библиотеке соответствующий профиль,
                                              проверьте материал»
        иначе если текущий ≠ ожидаемый → пометить к исправлению

если деталь — листовой металл:
    толщина := ISheetMetalFeatureData.Thickness × 1000 (мм)
    ожидаемый материал := поиск в библиотеке по «Типоразмер» среди листового проката
    далее так же
```

Затем — **в очереди простоя**: `IBody2.SetMaterialProperty` по телам с проверкой кода возврата, и при
изменениях `IBodyFolder.UpdateCutList()` — список вырезов сам не обновится.

## 7. Подводные камни, часть I

**П-1. Имена свойств списка вырезов переводятся по языку установки.** Проверено на боевых деталях: там
именно `ДЛИНА`, `УГОЛ1`, `Толщина листового металла`. Язык вмораживается в деталь при создании.
**Зашивать английские имена в код нельзя** — перебирать имена и сравнивать без учёта регистра по списку
на оба языка.

**П-2. Значения свойств хранятся формулами.** В списке вырезов лежит
`"SW-Material@@@Элемент списка вырезов1@…"`, а нужное значение — вычисленное. Читать надо разрешённое
значение, а не саму строку. У листовых деталей «Описание» вообще формула с подстановкой габаритов —
поэтому толщину берём из параметра элемента, а не из описания.

**П-3. Список вырезов может быть несвежим, и API не умеет это определить.** Видно прямо на боевых деталях:
у Стойки в одной папке `QUANTITY = 0`, встречаются пустые папки с двумя служебными свойствами.
Толщину и сечение берём из параметров элементов, которые всегда актуальны.

**П-4. Вызов сохранения изнутри обработчика сохранения — документированная бесконечная рекурсия.**
Защёлка от повторного входа обязательна.

**П-5. Назначение материала помечает документ изменённым.** Пользователь увидит «документ изменён» сразу
после сохранения. Это нормально, но об этом надо предупредить в руководстве.

**П-6. Имя файла профиля не уникально.** `40х20х1,5.sldlfp` лежит и в прямоугольных трубах, и в
плоскоовальных. Именно на этом построена ошибка 1. Сопоставлять по имени файла нельзя — только по
свойствам или по полному пути.

**П-7. Деталь только для чтения и деталь с внешними ссылками.** `SetMaterialProperty` вернёт отказ.
Надо не падать, а класть замечание.

# Часть II. Печать в цех

## 11. Как устроена книга ЛЗК

Книга собирается **поверх выгрузки SWTools**, а не с нуля:

1. надстройка просит SWTools выгрузить `Ведомость_<id>.xlsx` (`Sw\LzkService.cs:779-786`);
2. `LzkWorkbook.Complete` открывает её своим разбором (`Core\Lzk.cs:463-492`);
3. `LzkBook.Write` дописывает «Паспорт», четыре листа участков, «Расход», «Нормы»
   (`Core\LzkBook.cs:472-499`) и переносит «Паспорт» первым листом.

Порядок листов: **Паспорт, Ведомость, Заготовительный, Сварочный, Покрасочный, Комплектовочный,
Расход, Нормы**. Ориентация сейчас: **участки книжные** (`LzkBook.cs:802`), альбомный только «Расход».

Свой писатель `.xlsx` (`Core\Xlsx.cs`) умеет стили, объединение, закрепление областей, именованные
диапазоны, автофильтр, проверку ввода, формулы, **область печати и ориентацию**. Не умеет: вставлять
изображения и делать гиперссылки.

## 12. Кнопка в книге: прямо так — нельзя

Формат `.xlsx` по определению не хранит макросы. Нарисовать фигуру-кнопку можно, но назначить ей действие
нечем. Действие в книге бывает только у макроса (`.xlsm`), у гиперссылки или у надстройки Excel.

При этом макросы в файлах цеха **уже отклонены решением аудита** от 18.09; Excel в нашей автоматизации
запускается с принудительно выключенными макросами; а по регламенту (`РЕГЛАМЕНТ_КТО_v3.1:135`) стандартное
изделие печатает **начальник производства, у которого SolidWorks нет**. Последнее — ключевое: кнопка
именно в книге нужна потому, что у печатающего нет SolidWorks.

## 14. Эскизы на листах участков — решение владельца: не делать

Проработка сохранена для истории; **работы не ведутся**.

Обоснование решения владельца от 20.09: эскизы на всех четырёх участках — лишнее, картинка уже есть
в «Ведомости», и этого достаточно.

Что показала проработка и почему решение разумное:

* эскизы в «Ведомости» вставляет **SWTools**, не надстройка (решение Т4-2);
* правило выгрузки исключает стандартные, прочие, покупные изделия и материалы, поэтому **у покупных,
  материалов и самой сборки эскизов нет вообще** — «Комплектовочный» остался бы почти без картинок;
* **главная цена — бумага, а не байты**: чтобы эскиз было видно, строка становится втрое выше, и
  «Заготовительный» на изделии в 60 позиций уходит с 1–2 страниц на 4–5;
* писатель `.xlsx` вставлять картинки вообще не умеет — пришлось бы дописывать связи листа с рисунками,
  части с рисунками и привязку картинки к ячейке;
* буквы колонок в листах участков зашиты в формулы в девяти местах — вставка колонки задела бы все
  четыре ветки.

Для справки замеренные размеры: книга тестового изделия 64 897 Б, из них картинки 38 913 Б (60 %);
боевая книга «Стул NC3-7R» 254 050 Б, картинки 93 %.
