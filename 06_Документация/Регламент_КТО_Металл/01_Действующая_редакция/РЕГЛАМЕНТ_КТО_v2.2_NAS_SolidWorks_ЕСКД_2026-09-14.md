## ЧАСТЬ 1. АРХИТЕКТУРА ДАННЫХ

### 1.1. Принципы

1. **Одна копия данных.** Все модели, чертежи, эталоны и заказы живут только на NAS. Локальные копии CAD-данных не создаются, кроме личных черновиков (`D:\Work\_Черновики\`), которые не выдаются никому.
2. **Прямая работа по SMB без PDM.** SolidWorks открывает файлы с `Z:` напрямую. Так работает штатная блокировка: второй пользователь получает файл только для чтения и видит, кто его открыл. Цена выбора — риск порчи файла при обрыве сети во время сохранения. Этот риск принят сознательно, потому что порча видна сразу и восстанавливается, а рассинхрон локальных копий обнаруживается только в цеху. Меры — §2.7 и §4.11; условия перехода на PDM — §2.7.
3. **Инструментарий ЕСКД — одна общая папка для всех ПК.** Шаблоны, основные надписи, библиотека материалов, профили, база ТТ, надстройка ЕСКД и макросы SWplus лежат в `Z:\00_ИНСТРУМЕНТЫ\_Инструменты_Конструктора`. Конструктор один раз запускает из этой папки конфигуратор рабочего места. Конфигуратор прописывает в SolidWorks пути к `Z:` и регистрирует надстройку. Обновил администратор общую папку — обновились все ПК; для надстройки и макросов достаточно повторить ту же команду (§2.3). Реквизиты основной надписи, материал, масса и обозначения заполняются надстройкой автоматически при сохранении.
4. **Эталон не трогают.** Библиотека и база стандартов доступны конструкторам только для чтения; изменения в них вносит куратор баз по заявке.
5. **Повторное использование через исполнения.** Типоразмеры серийных изделий — конфигурации-исполнения в эталоне (ГОСТ 2.113), а не копии на каждый заказ.
6. **Ничего не удаляется без следа.** Снимки Btrfs, корзина общей папки, архив WriteOnce.

### 1.3. Жизненный цикл заказа

Каждая позиция служебной записки классифицируется по двум признакам.

| Стандартность | Что это | Что делает КТО |
| :--- | :--- | :--- |
| `СТД` — стандартное | серийное изделие из `02_БАЗА` без изменений | ничего не проектирует; техкарта и документы — из эталона по шифру и исполнению |
| `ТИПОВОЕ` | стандартное изделие с небольшими изменениями | копия сборки эталона и отвязка изменяемых деталей (§4.8) |
| `НЕСТАНДАРТНОЕ` | новое изделие без эталона | разработка с нуля по §4.4 |

| Направление | Папка в заказе | Чем проектируется |
| :--- | :--- | :--- |

### 2.3. Подключение ПК к инструментарию ЕСКД на сетевом диске

**Схема.** Инструментарий существует в одном месте — `Z:\00_ИНСТРУМЕНТЫ\_Инструменты_Конструктора`. На ПК конструктора его копии нет. Что откуда берётся:

| Компонент | Где лежит | Как работает на ПК |
| :--- | :--- | :--- |
| Шаблоны документов и свойств, основные надписи SWplus | `Z:` | пути SolidWorks указывают на `Z:` |
| Библиотека материалов, профили сварных деталей, профили резьбы, штриховки | `Z:` | пути SolidWorks указывают на `Z:` |
| База ТТ, словарь свойств `MyProperties_1.ini` | `Z:` | читаются с `Z:` |
| Design Library, Toolbox | `Z:\01_БИБЛИОТЕКА\` | пути SolidWorks указывают на `Z:` |
| Надстройка ЕСКД (`ESKD_Material_Sync_v5.dll`, `ESKD.exe`, `ESKD_Sync.exe`) | собрана администратором на `Z:` | конфигуратор копирует в `%LOCALAPPDATA%\ESKD\Toolkit\` и регистрирует оттуда |
| Макросы SWplus | `Z:` | **по умолчанию с `Z:`**: кнопки указывают на макросы в общей папке. Локальную копию получает только макрос, который при одновременной работе нескольких конструкторов пишет в свою папку, не работает при правах «только чтение» или мешает другим. Размещение каждого макроса задаёт матрица `swplus_macro_placement.json` по результатам проверки |
| Шрифты ГОСТ, модуль Drew | `Z:` | конфигуратор ставит в профиль пользователя |

**Почему надстройка копируется всегда, а макросы — только конфликтные.** Ограничения проверены по коду инструментария:

- SolidWorks держит DLL надстройки открытой, пока запущен. Если все 13 ПК грузят DLL с `Z:`, администратор не сможет её обновить, пока хоть у кого-то открыт SolidWorks (`03_Макросы_и_Плагины/ESKD_Material_Sync_Addin/build.ps1:25-29`).
- Часть макросов SWplus хранит настройки рядом с собой: `MProp.ini`, `DProp.ini`, `SProp.ini`, `SpecEditor.ini`, `TT.ini`, `SaveAsPDF.ini`. Макрос Master пересоздаёт файлы основных надписей. Такой макрос в общей папке либо не сохранит настройки при правах «только чтение», либо применит настройки одного конструктора у всех. Какие именно макросы конфликтуют, устанавливается проверкой на двух ПК; до неё решение не принимается.
- Надстройке нужны словарь свойств и списки фамилий рядом с собой, поэтому их служебная копия лежит в `%LOCALAPPDATA%\ESKD\Toolkit\` при любом размещении макросов. Общие списки фамилий и организаций ведёт администратор на `Z:`.
- Локальные копии обновляются конфигуратором по хешам выпуска, так что источник всё равно один.

**Порядок для конструктора (целевой).**

1. Открыть двойным щелчком конфигуратор рабочего места `Z:\00_ИНСТРУМЕНТЫ\_Инструменты_Конструктора\01_Настройки_SolidWorks\Настройка_Рабочего_Места_SolidWorks.exe`. Права администратора не нужны.
2. Проверить в окне фамилию и организацию. В шапке видно, установлен ли инструментарий и актуальна ли версия.
3. Нажать «Установить / Обновить». Если SolidWorks открыт, конфигуратор предложит закрыть его с сохранением.
4. Конфигуратор пропишет пути к `Z:`, скопирует надстройку и конфликтные макросы, направит 9 кнопок SWplus на сеть или на локальную копию, зарегистрирует надстройку, поставит шрифты и Drew, запишет фамилию и организацию. Ход и итог видны в окне.
5. Проверка: вкладка «ЕСКД» есть в детали, сборке и чертеже; в верхней панели 9 кнопок SWplus; в журнале `%TEMP%\eskd_material_sync.log` строка `=== ConnectToSW v6.0.0`.
6. Настройки, которые конфигуратор не задаёт, выставить по §2.4.

Когда шапка конфигуратора показывает «Требуется обновление», конструктор повторяет шаги 1–3. Шаблоны, библиотека материалов и сетевые макросы обновляются сразу, без повторного запуска. Кнопка «Системные компоненты…» нужна только для установки шрифтов в систему и требует учётных данных администратора.

**Порядок для администратора.**

1. Вносит изменения в репозиторий, запускает автотесты `python .\09_Тесты\run_tests.py full` на своём ПК.
2. При зелёном результате публикует выпуск скриптом публикации: сборка надстройки и конфигуратора, файл выпуска с хешами, копирование в `Z:\00_ИНСТРУМЕНТЫ\_Инструменты_Конструктора`. DLL на `Z:` никем не загружена, поэтому её замена безопасна; конфигуратор, открытый у пользователя, публикация перечислит как занятый файл.
3. Записывает версию и хеш из `build_manifest.json` в `00_ИНСТРУМЕНТЫ\_Журнал_ИТ.xlsx` и рассылает сообщение.
4. Списки фамилий и организаций SWplus (`MProp_Fam.txt`, `MProp_Firm.txt`) ведёт сам: у конструкторов на `Z:\00_ИНСТРУМЕНТЫ\` права только на чтение.

### 2.7. Работа по сети без PDM: защита от порчи файлов

**Почему это отдельный раздел.** Реселлеры Dassault прямо указывают, что редактирование файлов прямо на сервере SolidWorks поддерживает не полностью, а обрыв сети во время сохранения — самая частая причина порчи файлов (GoEngineer, GSC). Синхронизация локальных копий тоже не выход: она ломает блокировки и ссылки (Аудит, К-1…К-4). Без PDM регламент выбирает прямую работу и строит защиту в четыре слоя.

| Слой | Что делает | Где настроено |
| :--- | :--- | :--- |
| 1. Сеть без обрывов | Провод, без энергосбережения сетевых карт, актуальные драйверы, ИБП на NAS и коммутаторе | §2.1 п. 14, §2.2 |
| 2. Резервная копия SolidWorks | Перед каждым сохранением прежняя версия файла копируется в `C:\SW_Backup\` (3 копии) | §2.4 |
| 3. Снимки NAS | Каждый час; пользователь восстанавливает файл сам через «Предыдущие версии» | §2.1 п. 11 |
| 4. Процедура спасения | Порядок действий конструктора при ошибке сохранения | §4.11 |

**Журнал сбоев.** Администратор ведёт лист «Сбои сохранения» в `Z:\00_ИНСТРУМЕНТЫ\_Журнал_ИТ.xlsx`: дата, ПК, пользователь, файл, текст ошибки, чем восстановлен, потерянное время. Каждый случай разбирается: сеть, драйвер, антивирус, питание.

**Замеры на пилоте.** До ввода в работу и затем раз в квартал: время открытия самой тяжёлой сборки с `Z:` и с локального диска на одном ПК; результат — в журнал ИТ.

**Условия перехода на PDM Standard.** Решение принимает Начальник КТО по журналу. Пороги ниже — стартовые, уточняются по итогам пилота:

| Признак | Порог |
| :--- | :--- |
| Испорченные при сохранении файлы | более 1 случая в месяц после всех мер §2.2 |
| Открытие самой тяжёлой сборки с `Z:` | более чем вдвое дольше, чем с локального диска |
| Конфликты «кто открыл файл», срывающие сроки | еженедельно |
| Состав отдела | более 15 рабочих мест SolidWorks |

PDM Standard входит в лицензии SolidWorks Professional и Premium; для него нужен Windows-сервер с SQL Server Express. Дерево папок и имена файлов этого регламента переносятся в хранилище PDM без изменений.

### 2.8. Права доступа к папкам: как Начальник КТО выдаёт и снимает доступ

**Как устроены права.** Права на общие папки DSM с версии 5.0 — это Windows ACL: у каждой папки список записей «пользователь или группа — что разрешено». Подпапки наследуют записи родителя: в окне свойств унаследованные записи показаны серым, заданные на самой папке — чёрным. Разрешения суммируются: группе дано «Чтение», конкретному конструктору на подпапку — «Чтение» и «Запись», значит у него на этой подпапке чтение и запись. Если на уровне общей папки права пользователя и его группы противоречат, действует порядок «Нет доступа» → «Чтение/запись» → «Только чтение» (побеждает первое).

**Кто управляет правами.** Учётные записи DSM Начальника КТО и сисадмина входят в системную группу `administrators` (Панель управления → Пользователь и группа → пользователь → Изменить → вкладка «Группы пользователей» → `administrators`). Для них обязательна 2FA (§2.1, строка 10).

**Базовые права (настраивает сисадмин один раз):**

| Папка | kto_admins | kto_kurator | kto_metall, kto_korpus | kto_tech | production | prod_view |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `KTO` (корень общей папки) | Чтение и запись | Только чтение | Только чтение | Только чтение | только просмотр корня: «Настроить» → «Применить к: эта папка» → «Чтение» | как у `production` |
| `00_ИНСТРУМЕНТЫ` | Чтение и запись | Только чтение | Только чтение | Только чтение | нет | нет |

| `03_ЗАКАЗЫ` | Чтение и запись | Только чтение | Только чтение | Только чтение | нет | нет |

| Где | Флажок | Ставить? | Зачем |

**Правила.**

1. Никогда не использовать тип записи «Запретить» (Deny) — отозвать доступ удалением записи.
2. Никогда не выдавать конструктору разрешение «Администрирование» — с ним он сам меняет права.
3. Не разрывать наследование: права задаются добавлением записей, а не удалением унаследованных.
4. Каждая выдача и снятие — строка на листе «Доступы» журнала ИТ `Z:\00_ИНСТРУМЕНТЫ\_Журнал_ИТ.xlsx`: дата, кто выдал, кому, папка, права, основание (заказ или ИИ), срок, дата снятия.
5. Новые права действуют при следующем открытии файлов и папок. Если конструктор уже открыл сборку, пусть закроет её и откроет снова; если доступа всё равно нет — выйти из Windows и войти заново.

Названия пунктов ниже даны по смыслу русского интерфейса DSM 7.2 и могут немного отличаться в вашей версии; порядок действий совпадает с базой знаний Synology.

**Процедура А. Выдать исполнителю запись в папку заказа** (Начальник КТО, при назначении исполнителя, §3.2 шаг 3):

1. Войти в DSM: `https://nas-kto:5001` → File Station.
2. Открыть `KTO` → `03_ЗАКАЗЫ`, выделить папку заказа `250-АСТ_Школа12`.
3. ПКМ → «Свойства» → вкладка «Разрешение» → «Создать».
4. В окне «Редактор разрешений»: «Пользователь или группа» — учётная запись исполнителя; «Тип» — «Разрешить»; «Применить к» — «Эта папка, дочерние папки, дочерние файлы» (все потомки); «Разрешение» — отметить **«Чтение»** и **«Запись»** целиком, «Администрирование» не отмечать → «Готово».
5. «Сохранить». Если DSM спрашивает, применить ли к подпапкам и файлам, — ответить «Да» (флажок «Применить к этой папке, подпапкам и файлам»).
6. Проверить процедурой Г; запись на листе «Доступы».

**Процедура Б. Снять запись** (при закрытии заказа, при замене исполнителя, по окончании срока ИИ):

1. File Station → папка → «Свойства» → «Разрешение».
2. Выделить **чёрную** (заданную на этой папке) запись пользователя → «Удалить» → «Сохранить». Серые записи групп не трогать.
3. Проверить процедурой Г; дата снятия на листе «Доступы».

**Процедура В. Временная запись в эталон `02_БАЗА`** (исполнителю извещения об изменении, если это не куратор баз, §6.5 шаг 3): как процедура А, но на папку изделия `02_БАЗА\01_Столы\СТД-СЛ120.00`; срок — срок извещения; после внедрения — процедура Б.

**Процедура Г. Проверить, какие права у конструктора на самом деле:** File Station → папка → «Свойства» → «Разрешение» → «Дополнительные параметры» → «Инспектор разрешений» (Permission Inspector) → выбрать пользователя → в поле ниже видны итоговые «Администрирование», «Чтение», «Запись».

**Процедура Д. Сотрудник пришёл или ушёл** (сисадмин по распоряжению Начальника КТО):

- Пришёл: Панель управления → Пользователь и группа → «Создать» → логин = логин Windows (§2.1, строка 2) → группа по должности (`kto_metall`, `kto_korpus`, `kto_tech`). Персональных записей в ACL не создавать, пока он не назначен исполнителем.
- Ушёл: отключить учётную запись (не удалять — иначе в ACL и журналах останутся «Неизвестные» записи); снять его явные записи со всех папок процедурой Б по листу «Доступы».

**Процедура Е. Веб-доступ начальника производства** (сисадмин по распоряжению Начальника КТО; инструкция пользователя — И-09):

1. Пользователь начальника производства — только в группе `prod_view`, других групп нет (при конфликте «Запретить» сильнее «Разрешить»).
2. Права по таблице выше: корень `KTO` — чтение «только эта папка»; `02_БАЗА` и `04_ПРОИЗВОДСТВО` — чтение для всех потомков.
3. Панель управления → **Привилегии приложений** (Application Privileges) → приложение → «Изменить» → «Группа» → `prod_view`: **File Station** — «Разрешить», при наличии варианта «По IP» — только подсеть офиса; **DSM**, если такой пункт есть в списке, — «Разрешить»; **SMB**, **AFP**, **FTP**, **WebDAV**, **Synology Drive** и прочие — «Запретить».
4. Проверка: «Привилегии приложений» → «Просмотр разрешений» → пользователь и IP его ПК; затем вход с его ПК на `https://nas-kto:5001`: видны только File Station и папки `02_БАЗА`, `04_ПРОИЗВОДСТВО`, загрузка файла — отказ.
5. Запись на листе «Доступы».

Доступ работает только из сети предприятия: внешний доступ NAS выключен (§2.1, строка 8). Доступ из-за пределов предприятия — отдельное решение о VPN. Незавершённые заказы `03_ЗАКАЗЫ` начальнику производства не открываются: по неутверждённым документам работать нельзя; если нужен и этот просмотр — добавить `prod_view` чтение на `03_ЗАКАЗЫ` решением Начальника КТО.

**Альтернатива — Проводник Windows.** Права можно менять и с ПК через Проводник: ПКМ по папке на `Z:` → «Свойства» → «Безопасность» → «Изменить» → «Добавить» → учётная запись NAS → отметить «Изменение» в столбце «Разрешить» → «ОК». Основной способ регламента — File Station: там видны унаследованные записи и есть «Инспектор разрешений».

Pack and Go перепривязывает ссылки на новое место и собирает детали из `02_БАЗА`; простое копирование папки изделия теряет эталонные детали. Возврат изменений от подрядчика — через приёмку §3.3, а не копированием поверх.
8. Решение по каждому предложению об изменении эталона `02_БАЗА`, утверждение извещений об изменении, временный доступ исполнителям (§6.5).
9. Контроль журналов изменений заказов после выдачи в производство (§6.4).

### 3.2. Пошаговый маршрут

- **Шаг 1. Задача и папка заказа.** Служебная записка и задача с исполнителями — в Битрикс24. Папку заказа создать скриптом:
  ```powershell
  powershell -ExecutionPolicy Bypass -File "Z:\00_ИНСТРУМЕНТЫ\Шаблоны_заказа\New-OrderFolder.ps1" -Number 250-АСТ -Object Школа12
  ```
  Скрипт (Приложение А) создаёт дерево §1.2, копирует шаблоны `Разметка_СЗ.xlsx` и `Журнал_изменений.xlsx`, проверяет длину пути. Положить `СЗ_250-АСТ.pdf` в корень.
- **Шаг 2. Разметка СЗ (5–10 мин).** Заполнить `Разметка_СЗ.xlsx` по §5.1: для каждой позиции — стандартность, направление, шифр, эталон, исполнение, тираж, RAL и ссылка на задачу Битрикс24. Исполнителей и сроки в разметку не вносить.
- **Шаг 3. Папки изделий.** Для каждой позиции `ТИПОВОЕ` и `НЕСТАНДАРТНОЕ`, с направлением из разметки:
  ```powershell
  powershell -ExecutionPolicy Bypass -File "Z:\00_ИНСТРУМЕНТЫ\Шаблоны_заказа\New-OrderFolder.ps1" -Number 250-АСТ -Object Школа12 -Product "И01_Стол_L1400" -Designation "250-АСТ-Т01.00" -Direction Металл
  ```
  `-Direction Корпус` создаёт папку в `01_Корпус\`. Для изделия `КОМБИ` скрипт запускается для каждого направления, где есть работа: конструкторы делают свою часть каждый в своей папке, а кто финализирует общую сборку и техкарту изделия, конструкторы решают сами и отмечают в задаче Битрикс24.

### 4.2. Имена файлов и обозначения (регламент инструментария ЕСКД, ч. I, §4)

| Тип | Шаблон имени | Пример |
| :--- | :--- | :--- |
| Деталь | `Обозначение Наименование.sldprt` | `250-АСТ-Т01.10.01 Столешница.sldprt` |
| Сборка | `Обозначение СБ Наименование.sldasm` | `250-АСТ-Т01.00 СБ Стол ученический L1400.sldasm` |
| Чертёж | как у модели | `250-АСТ-Т01.10.01 Столешница.slddrw` |
| Эталон базы | `СТД-<серия><номер>.<узел>.<деталь>` | `СТД-СЛ120.10.01 Столешница.sldprt` |

Разделитель — первый пробел; подчёркивания в имени файла не применяются (надстройка делит имя по пробелу). Обозначение всегда содержит цифры. Схема обозначения заказа: `<№ заказа>-<Тип><№ изделия>.<узел>.<деталь>`; узел `00` — изделие в целом.

**Исполнения** (ГОСТ 2.113): конфигурации `00` (базовое), `01`, `02` … Надстройка сама пишет `Обозначение-01`, `-02` в конфигурации. Столы L1200/L1400/L1600 в эталоне — одно изделие `СТД-СЛ120.00` с исполнениями `00/-01/-02`; заказ на L1400 — позиция `[СТД]` с исполнением `-01`, проектировать ничего не нужно.

После переименования файла в Проводнике, «Сделать независимым» или Pack and Go надстройка считает старое обозначение ручным (Руководство, ч. I, §4.3): очистить `Обозначение` и `Наименование` в MProp и сохранить — реквизиты возьмутся из нового имени.

### 4.4. Подетальная сборка: основной способ и исключение

**Основной способ — скелет и независимые детали.** Обязателен для серийных изделий: столы, парты, стеллажи, стулья, подстолья, торговое оборудование. В сборке изделия создаётся компоновочный эскиз (skeleton) с габаритами; детали строятся по эскизу; каждая труба, стойка, косынка — отдельный `.sldprt` по §4.2 со своими эскизами и размерами. После выпуска контекстные ссылки на скелет блокируются (ПКМ по детали → «Внешние ссылки» → «Заблокировать все»), чтобы деталь можно было заимствовать отдельно по §4.8.

**Исключение — сварная деталь и Save Bodies.** Допускается только для нерегулярных пространственных рам, где скелет из плоских эскизов построить нельзя, и только по согласованию с Начальником КТО. Ограничения способа (Заключение, З-3; справка SolidWorks):

- производная деталь не имеет своих эскизов и размеров, в её дереве только ссылка на мастер;
- изменение мастера меняет **все** производные детали;
- копии производных деталей, сделанные через Pack and Go или «Сохранить как копию», продолжают ссылаться на исходный мастер;
- поэтому такая деталь **не заимствуется по §4.8**: отвязать одну царгу и изменить только её нельзя.

Порядок, если исключение согласовано: мастер `250-АСТ-Т01.10 Рама (мастер).sldprt` в подпапке `01_3D\_Мастер\` (в спецификацию не входит) → ПКМ по папке «Список вырезов» → «Сохранить тела»: ☑ «Создавать производные детали из подобных тел», ☑ «Копировать свойства списка вырезов», ☑ «Создать сборку» → `250-АСТ-Т01.10 СБ Рама.sldasm`; имена тел — сразу по §4.2. Затем открыть каждую производную деталь, проверить материал из библиотеки, сохранить. При заимствовании такой рамы в другой заказ копируется **весь узел вместе с мастером** через Pack and Go.

Многотельная деталь без Save Bodies допускается только для концептов в `_Черновики`.

**Длина заготовки.** В каждой детали из проката добавить эскиз `Примечания` со справочным размером `RD1` — длиной заготовки: надстройка использует его для записи БЧ и его же читает скрипт свода (лист «Заготовка»).

### 4.5. Безчертёжные детали (БЧ)

Прямой отрезок трубы, полоса, пластина без отверстий — оформляются без чертежа: назначить материал, сохранить по регламенту имён, нажать «Деталь БЧ» на вкладке ЕСКД. Надстройка запишет `Формат` = БЧ, массу в «Примечание», наименование в три строки (наименование / дробь материала / `L = … мм`). Для БЧ-деталей выпускаются только файлы ЧПУ (§4.9) — чертёж не нужен, это снимает до половины чертежей с типового стола.

Перенос Проводником запрещён (К-6).

### 4.8. Типовое изделие: пошаговое заимствование из эталона

Раздел применяется к изделиям `ТИПОВОЕ`. Изделие `НЕСТАНДАРТНОЕ` не имеет эталона: оно разрабатывается с нуля по §4.2–4.7, а для повторного использования в будущих заказах Начальник КТО может передать его куратору баз как новый эталон (И-03).

**Принцип.** Заранее неизвестно, какие детали затронет доработка: изменение столешницы тянет траверсу, траверса — косынку. Поэтому копируется **только сборка**, а детали отвязываются по одной в тот момент, когда их действительно нужно менять. Перечень выпускаемых деталей получается в конце работы, а не угадывается в начале.

**Страховка.** `Z:\02_БАЗА` доступна только для чтения. Изменить и сохранить эталонную деталь невозможно: при попытке SolidWorks сообщит, что файл только для чтения. Это и есть сигнал «эту деталь нужно отвязать».

**Шаг 1. Копия сборки (1 мин).**

1. Окно → Закрыть все. Открыть `Z:\02_БАЗА\01_Столы\СТД-СЛ120.00\01_3D\СТД-СЛ120.00 СБ Стол ученический.sldasm` (откроется только для чтения).
2. Файл → **Сохранить как** (не «как копию») → папка `Z:\03_ЗАКАЗЫ\250-АСТ_Школа12\02_Металл\И01_Стол_L1400\01_3D\` → имя `250-АСТ-Т01.00 СБ Стол ученический L1400.sldasm`. В разделе «Дополнительно» флажок «Включить все ссылочные компоненты» — **снят**.
3. MProp → очистить «Обозначение» и «Наименование» → Ctrl+S (надстройка заполнит реквизиты по новому имени, §4.2).
4. Проверка: Файл → Открыть → «Ссылки…» — все детали указывают на `Z:\02_БАЗА\…`. Ни одна деталь не скопирована.

**Шаг 2. Отвязка детали — каждый раз, когда её нужно изменить.**

1. В дереве сборки ПКМ по детали → **«Сделать независимым»** (Make Independent). Меняются все экземпляры детали — выделить все экземпляры (Ctrl+клик) до команды. Меняется только часть экземпляров — выделить только их, остальные останутся эталонными.
2. В окне сохранения **сменить папку**: SolidWorks предлагает папку исходного файла, то есть `02_БАЗА`, куда записи нет. Указать `…\И01_Стол_L1400\01_3D\` и имя по §4.2: `250-АСТ-Т01.10.01 Столешница.sldprt`.
3. Открыть новую деталь → MProp → очистить «Обозначение» и «Наименование» → Ctrl+S.
4. Только теперь менять размеры. Ctrl+Q, Ctrl+S — деталь, затем сборка.
5. Изменение потянуло соседнюю деталь — повторить шаг 2 для неё. Сколько нужно раз, столько и повторять.

**Детали из Save Bodies.** Этот порядок к ним не применяется: производная деталь зависит от мастера (§4.4). Узел из Save Bodies заимствуется целиком, Pack and Go вместе с мастером.

**Деталь внутри эталонного узла.** Сначала отвязать узел (шаг 2 для подсборки), затем деталь внутри него. Файл эталонного узла только для чтения, и замену детали в нём сохранить нельзя. Порядок всегда сверху вниз: изделие → узел → деталь.

**Правка сделана до отвязки.** Если SolidWorks при сохранении сообщил, что эталонная деталь только для чтения, выполнить для неё шаг 2 и открыть новую деталь. Правка на месте — продолжать. Правки нет — повторить её в новой детали. Эталон при этом не пострадал.

**Отвязали лишнее.** Деталь отвязана, но в итоге не изменилась: ПКМ → «Заменить компоненты» → выбрать эталонный файл из `02_БАЗА` → ☑ «Все экземпляры» → сохранить сборку → удалить неиспользуемую копию из `01_3D\`, предварительно проверив «Ссылками…», что на неё никто не ссылается.

**Шаг 3. Чертежи отвязанных деталей и сборки.** «Сделать независимым» чертёж не копирует, поэтому чертёж переносится с эталона:

1. Открыть чертёж эталонной детали `Z:\02_БАЗА\…\01_3D\СТД-СЛ120.10.01 Столешница.slddrw`.
2. Файл → **Сохранить как** → `…\И01_Стол_L1400\01_3D\250-АСТ-Т01.10.01 Столешница.slddrw`. С этого момента открыт новый чертёж, эталон не тронут.
3. ПКМ по любому виду → **«Заменить модель»** (Инструменты → Заменить модель) → ☑ все виды → выбрать новую деталь `250-АСТ-Т01.10.01 Столешница.sldprt` → ОК.
4. Проверить оборванные (оливковые) размеры и примечания, поправить, обновить ТТ, Ctrl+S.
5. Так же для сборочного чертежа: эталонный СБ-чертёж → «Сохранить как» → «Заменить модель» на новую сборку → обновить спецификацию SpecEditor и позиции.

**Шаг 4. Перечень к выпуску — в конце работы.** Файл → Открыть → сборка → «Ссылки…». Всё, что лежит в папке изделия, — новое: на него выпускается чертёж или оформляется БЧ (§4.5), делаются файлы ЧПУ (§4.9) и строки техкарты. Всё, что лежит в `02_БАЗА`, берётся из эталона: в техкарте ссылка на эталонные PDF.

**Когда уместен Pack and Go.** Только если состав изменений известен заранее целиком: повтор изделия из прошлого заказа (Pack and Go всего изделия с новым префиксом) или передача изделия подрядчику.

**Автоматизация.** Ручной шаг 3 закрывает задача Д-53 — команда «Сделать независимым с чертежом» на вкладке ЕСКД. Она копирует чертёж рядом с новой моделью, перепривязывает его и очищает реквизиты для заполнения по имени.

### 4.9. Выдача в производство: форматы, имена, ревизии

| Формат | Папка | Как получить | Имя файла | Потребитель |
| :--- | :--- | :--- | :--- | :--- |
| PDF | `02_PDF\` | макрос **SaveAsPDF** (кнопка 9 SWplus) из чертежа | `<Обозначение> <Наименование>_Изм0.pdf` | сборка, сварка, ОТК |
| DXF (лист) | `03_ЧПУ\` | ПКМ по плоской грани развёртки → «Экспорт в DXF/DWG»: выход «Развёртка», ☐ линии сгиба, ☐ эскизы, ☑ геометрия; версия R2000, мм, 1:1; сплайны → полилинии, если требует CypNest | `<Обозначение>_S<толщина>_<марка>_x<шт на изделие>.dxf` → `250-АСТ-Т01.10.01_S3_Ст3сп_x1.dxf` | лазер CypCut/CypNest |
| IGS (труба) — единственный формат для своих станков | `03_ЧПУ\` | Файл → Сохранить как → IGES (*.igs) → «Параметры»: вывод твёрдых тел и поверхностей, тип сущностей и единицы (мм) — по «Матрице форматов ЧПУ»; «Вывод системы координат» — система координат вдоль оси трубы | `<Обозначение>_<профиль>_L<длина>_x<шт>.igs` → `250-АСТ-Т01.20.01_Тр40х40х2_L1350_x2.igs` | труборезы КТО (CypTube, TubePro, TubesT) |
| STEP / SAT (труба) | `03_ЧПУ\_Подрядчик\` | Файл → Сохранить как → STEP AP214 или ACIS (*.sat); система координат — как для IGS | как для IGS, расширение `.step` / `.sat` | только сторонний подрядчик по его письменному требованию |

**Почему один формат.** Руководство TubesT указывает IGS как формат, из которого делаются файлы резки CypTube, а SAT — только для раскладки в TubesT. Когда в `03_ЧПУ\` лежат три расширения, оператор тратит время на подбор. Поэтому для своих станков выдаётся только IGS. Для справки — что читают распространённые программы:

| ПО трубореза | IGS | SAT | STEP | Прочее | Источник |
| :--- | :---: | :---: | :---: | :--- | :--- |
| Friendess CypTube (стойка станка) | да — источник файла резки | нет | нет | CTD, CTDS | руководство TubesT |
| Friendess TubesT (раскладка, ПК) | все версии; ось трубы строго вдоль X/Y/Z | с V1.13 (ACIS 16.0 из SolidWorks 2016+) | с V1.47 | IFC, NC1 (Tekla) | документация Bochu, руководство TubesT |
| Lantek Flex3d Tubes | да | да | да | модели SOLIDWORKS | сайт Lantek |
| BLM ArTube | да | не заявлен | да | XT (Parasolid), IFC | сайт BLM |

Правила:

1. Для станков КТО выгружается **только IGS**. SAT и STEP в `03_ЧПУ\` не кладутся; для подрядчика — отдельная подпапка `_Подрядчик\`.
2. Технолог ведёт `Z:\00_ИНСТРУМЕНТЫ\Матрица_форматов_ЧПУ.xlsx`: станок, ПО и его версия, **утверждённые настройки экспорта IGES** (вывод тел или поверхностей, тип сущностей, единицы), кто и когда проверил.
3. Настройки экспорта утверждаются пробным импортом трёх деталей: прямой рез, рез под углом, отверстия на двух гранях. Если импорт проходит в нескольких вариантах, выбирается тот, где TubesT без правок распознаёт сечение и все резы. Конкретный тип сущностей IGES производитель не оговаривает, поэтому он фиксируется только по результату пробы.
4. Ось трубы вдоль оси координат обязательна для IGS. Деталь, построенная по скелету наклонно, экспортируется с системой координат вдоль её оси, выбранной в поле «Вывод системы координат».
5. Признак неудачного импорта в TubesT — сечение `0.00 x 0.00 x 0.00`. Такой файл возвращается конструктору.

Ревизии: первая выдача — `_Изм0`; каждое изменение после выдачи — следующий номер `_Изм1`, `_Изм2` …; прежний файл переносится в `_Аннулировано\`. Модели не переименовываются. Когда и как оформлять изменение — часть 6.

### 4.11. Ошибка при сохранении: спасение файла

Признаки: окно «Произошла ошибка при сохранении файла» (An error was encountered while trying to save your file), зависание сохранения, пропадание `Z:` в Проводнике.

1. **Не закрывать SolidWorks** и не нажимать «Не сохранять». В памяти остаётся целая модель.
2. Файл → **Сохранить как копию** (Save as Copy) → `C:\SW_Rescue\` под тем же именем. Именно «как копию»: открытый документ и его ссылки остаются на `Z:`. Если в сборке изменены и другие несохранённые детали, так же сохранить копию каждой, открыв её.
3. Проверить `Z:` в Проводнике и сам файл: открывается ли он и не нулевой ли у него размер.
4. Сеть на месте и файл целый — повторить Ctrl+S и продолжить работу. Запись в журнал всё равно сделать (п. 6): сбой без порчи тоже признак проблемы.
5. Файл на `Z:` испорчен — закрыть документ, восстановить в таком порядке: спасённая копия из `C:\SW_Rescue\` → последняя копия из `C:\SW_Backup\` → снимок NAS через «Предыдущие версии». Положить восстановленный файл на место испорченного, открыть сборку, проверить «Ссылки…».
6. Сообщить администратору: запись в лист «Сбои сохранения» журнала ИТ (§2.7).
7. Папку `C:\SW_Rescue\` очистить после восстановления, чтобы там не копились устаревшие версии.

### 5.3. Скрипт свода `Свод_заявки.py` (детерминированный, без ИИ)

- **Вход:** `Разметка_СЗ.xlsx` заказа; техкарты по `Шифр`+`Исполнение`: для `СТД` — из `Z:\02_БАЗА\**\Техкарта_<Шифр>_на_1шт.xlsx`, для `ТИПОВОЕ` и `НЕСТАНДАРТНОЕ` — из папки изделия заказа (у `КОМБИ` — из той папки направления, где техкарта заполнена; если заполнены обе — останов с указанием позиции). Позиции `КОРПУС` без техкарты по схеме §5.2 не останавливают свод, а выводятся на лист `Проверки` как «без техкарты».
- **Логика:** умножить каждую строку на `Тираж`; сгруппировать лист 1 по `Материал_Строка` и толщине/профилю; лист 3 — по RAL; лист 5 — суммы по `Материал_Строка`; добавить лист `Комплект` — перечень PDF/DXF/IGS с путями (для СТД — из `02_БАЗА`).
- **Выход:** `Заявка_<№>.xlsx` в корне заказа с теми же 5 листами + `Комплект` + `Проверки`.
- **Нормализация шифров (перед поиском техкарт):** у `Шифр` и `Исполнение` убираются пробелы по краям и двойные пробелы; для сравнения шифр приводится к верхнему регистру, а латинские буквы, похожие на кириллицу (A B C E H K M O P T X Y), заменяются кириллическими. Нормализуется **только шифр** и только для сравнения: `RAL`, имена файлов и прочие поля не трогаются. Нормализованный шифр сравнивается с так же нормализованными именами техкарт. Каждое исправление выводится на лист `Проверки` с номером строки («строка 7: «CТД-СЛ120.00 » → найдено «СТД-СЛ120.00»»), чтобы разметку поправили в источнике.
- **Проверки (останов при ошибке):** у всех позиций заполнены `Стандартность`, `Направление`, `Шифр`, `Тираж`; у `ТИПОВОЕ` — `Эталон`; у `МЕТАЛЛ` и `КОМБИ` — `RAL`; техкарта найдена для каждой позиции; в техкарте нет пустых `Материал_Строка`; обозначения из техкарты существуют как файлы в `01_3D` (для `ТИПОВОЕ` и `НЕСТАНДАРТНОЕ` с металлом); сумма масс листа 1 ≈ масса сборки ±5 %.
- **Запуск:** Начальник КТО или технолог, вручную, из папки заказа:
  ```powershell
  python "Z:\00_ИНСТРУМЕНТЫ\_Инструменты_Конструктора\10_Свод_заявки\Свод_заявки.py" "Z:\03_ЗАКАЗЫ\250-АСТ_Школа12"
  ```
- **Ответственность:** технолог (ЕСТД, ГОСТ 3.1118) проверяет листы 1–5, Начальник КТО утверждает. Файл в `04_ПРОИЗВОДСТВО` — единственный документ для цехов, ОМТС и 1С.
- **ИИ:** допускается только для черновой выписки позиций из PDF служебной записки в `Разметка_СЗ.xlsx` с обязательной правкой человеком; данные заказчика во внешние сервисы не передаются без письменного соглашения о необработке. Google Antigravity и подобные среды разработки к производственному контуру не относятся.
- **Статус:** скрипт и шаблоны техкарт — задача инструментария ЕСКД (Д-47); до её закрытия свод выполняется технологом вручную по той же схеме листов.

## ЧАСТЬ 6. ИЗМЕНЕНИЯ И РЕВИЗИИ КОНСТРУКТОРСКОЙ ДОКУМЕНТАЦИИ

### 6.1. Основа и главные правила

Часть основана на ГОСТ 2.503-2013 «ЕСКД. Правила внесения изменений». Казахстана нет среди государств, проголосовавших за этот стандарт; раздел 1 стандарта разрешает разрабатывать на его основе стандарты организаций. Поэтому его правила применяются в КТО как корпоративные, в объёме ниже.

1. **Изменение** — любое исправление, исключение или добавление данных в документ (ГОСТ 2.503, п. 4.1). Правка до выдачи в производство изменением не считается и ревизию не создаёт.
2. **Выдача в производство** — момент, с которого документ становится подлинником: для заказа — копирование комплекта в `04_ПРОИЗВОДСТВО` (§3.2, шаг 7); для эталона — утверждение Начальником КТО и размещение в `02_БАЗА`.
3. **Взаимозаменяемость.** Изменение вносится в документ, только если новое изделие взаимозаменяемо с изготовленными раньше. Если нет — выпускается документ с новым обозначением или новое исполнение по ГОСТ 2.113 (п. 4.2, 4.5). Решение — по §6.2.
4. **Связанные документы меняются одновременно**: модель, чертёж, DXF/IGS, сборочный чертёж и спецификация, если меняется состав, техкарта, если меняются нормы (п. 4.3).
5. **Применяемость.** Если документ входит в несколько изделий и хотя бы одному изменение не подходит — новое обозначение (п. 4.4). Для эталонов применяемость проверяется по §6.6.
6. **Электронный документ** меняется выпуском новой версии; в реквизитах указывается только последнее изменение (п. 4.6, 5.3).
7. **Номер изменения** — порядковый, арабскими цифрами: 1, 2, 3… Один номер получают все изменения документа по одному основанию; номер свой у каждого документа (п. 5.10).
8. **Вносит изменения только держатель подлинников**: в `02_БАЗА` — куратор баз или назначенный Начальником КТО исполнитель с временным доступом; в заказе — исполнитель заказа (п. 4.7).
9. **Основание изменения**: для эталона — извещение об изменении (ИИ); для документов заказа (единичное производство в одной организации) — запись в журнале изменений заказа без ИИ (п. 4.9, приложение Г).
10. **Ошибка в изменении** исправляется новым изменением, а не правкой прежней записи (п. 4.16). Если ошибка в документе, находящемся в цеху, может дать брак — исправление вносится в копию в цеху немедленно под подпись ответственных, оформление следует за ним (п. 4.18).

### 6.2. Изменение или новое обозначение

**Главный вопрос:** можно ли деталь, изготовленную по старому документу, поставить в новое изделие, а деталь по новому документу — в изделие, собранное раньше? Да — оформляется изменение. Нет — новое обозначение.

| Что меняется | Взаимозаменяемость | Решение |
| :--- | :--- | :--- |
| Ошибка в чертеже при правильной детали (размер проставлен неверно, опечатка в ТТ, не та ссылка на ГОСТ) | не затрагивается | изменение, код причины 7 |
| Радиус гиба, фаска, технологический вырез, покрытие, не влияющие на сборку и сопряжения | сохраняется | изменение |
| Дополнительное отверстие, не мешающее сборке старых изделий | сохраняется | изменение |
| Присоединительные размеры, шаг и диаметр отверстий под крепёж, длина, толщина, профиль, марка стали, влияющие на сборку, прочность или массу | **нарушена** | новое обозначение: новое исполнение `-0N` эталона (§4.2) или новый документ; старый документ не меняется |
| Изменение нужно только одному заказу | — | эталон не менять; «Сделать независимым» в заказе (§4.8) |
| Изменение нужно одним заказам и недопустимо для других | — | новое обозначение (п. 4.4 ГОСТ 2.503) |

Сомнение решает Начальник КТО; решение записывается в извещение (§6.7) или журнал заказа.

### 6.3. Где фиксируется ревизия

| Что | Где | Как |
| :--- | :--- | :--- |
| Номер изменения чертежа | таблица изменений основной надписи (графы «Изм.», «Лист», «№ докум.», «Подп.», «Дата» по ГОСТ 2.104) | «Изм.» — номер изменения; «Лист» — прочерк для однолистового документа, «Зам.» или «Нов.» для заменённых и новых листов многолистового; «№ докум.» — обозначение ИИ (`ИИ-КТО-2026-004`) или номер записи журнала заказа (`Ж-250-АСТ-3`); подпись и дата. В словаре свойств SWplus полей для этой таблицы нет: до выполнения Д-60 графы заполняются заметками чертежа вручную |
| Выдаваемые файлы | `02_PDF\`, `03_ЧПУ\` | суффикс `_ИзмN` в имени; файлы предыдущей ревизии переносятся в `_Аннулировано\` рядом |
| Модели и чертежи SolidWorks | те же файлы | имена не меняются. Для эталонов прежняя версия сохраняется в `_Версии\Изм<N-1>\` (§6.5, шаг 5) |
| Основание | эталон — ИИ в `02_БАЗА\_Извещения\`; заказ — строка `Журнал_изменений.xlsx` | формы §6.7 |
| История | эталон — `История_изменений.xlsx` в папке изделия; заказ — тот же журнал | одна строка на изменение |

Исходный выпуск имеет суффикс `_Изм0` и пустую таблицу изменений. Первое изменение — `Изм. 1`.

### 6.4. Порядок: изменение документов заказа после выдачи в производство

Выполняет исполнитель заказа. Основание — журнал изменений заказа (ИИ не выпускается).

1. **Если деталь уже в работе и ошибка даст брак** — сразу сообщить мастеру участка и технологу, затем Начальнику КТО. Мастер останавливает операцию по этой детали.
2. **Запись в журнал.** `Z:\03_ЗАКАЗЫ\<заказ>\Журнал_изменений.xlsx`, лист «Изменения»: номер записи, дата, обозначение документа, содержание изменения (было → стало), указание о заделе — что делать с уже изготовленными деталями (использовать, доработать, в брак). Статус «В работе».
3. **Согласование.** Если изменение затрагивает другое изделие заказа, техкарту, покупные или срок — отметка Начальника КТО в записи до продолжения работ.
4. **Изменение моделей и чертежей.** Внести правку, Ctrl+Q, «Синхронизировать» на вкладке ЕСКД, заполнить таблицу изменений (§6.3), Ctrl+S. Связанные документы — по §6.1, п. 4.
5. **Файлы выдачи.** Новые PDF, DXF, IGS с суффиксом `_ИзмN`; прежние — в `_Аннулировано\` папки изделия.
6. **Техкарта и свод.** Если изменились нормы или состав — поправить техкарту и перезапустить свод заявки (§5.3). Новая заявка сохраняется как `Заявка_250-АСТ_ИзмN.xlsx`.
7. **Нормоконтроль** изменённого чертежа (подпись в основной надписи).
8. **Замена в цеху.** Начальник КТО или технолог копирует новые файлы в `04_ПРОИЗВОДСТВО\<заказ>\`, прежние (включая прежнюю заявку) переносит там в `_Аннулировано\`, сообщает мастеру и ОМТС. Бумажные копии в цеху заменяются новыми распечатками, старые изымаются.
9. **Закрытие записи.** В журнале отметки «внесено в подлинники» (модель, чертёж) и «внесено в копии» (`04_ПРОИЗВОДСТВО`, цех), статус «Внедрено».

### 6.5. Порядок: изменение эталона в `02_БАЗА` (например, найден дефект)

Роли: **инициатор** — любой сотрудник; **Начальник КТО** — решение и утверждение; **куратор баз** — держатель подлинников эталонов, вносит изменения или передаёт это назначенному конструктору; **технолог** — задел и нормы; **нормоконтроль**.

1. **Предложение.** Инициатор записывает дефект в `Z:\02_БАЗА\_Извещения\Книга_регистрации_ИИ.xlsx`, лист «Предложения»: дата, кто, шифр изделия, документ, в чём дефект, скриншот или фото. Сам эталон не правит — прав на запись нет. Если дефект даст брак в заказе, который сейчас в цеху, — действовать как в §6.4, шаг 1.
2. **Решение Начальника КТО** (не позднее следующего рабочего дня): изменение или новое обозначение (§6.2); какие открытые заказы затронуты и что с ними делать (§6.6); исполнитель; срок; номер ИИ по книге регистрации (лист «Извещения», следующий свободный `ИИ-КТО-2026-NNN`).
3. **Доступ.** Если исполнитель — не куратор баз, Начальник КТО выдаёт ему временную запись на папку изделия (§2.8, процедура В).
4. **Защита заказов, которым нужна прежняя ревизия** (решение шага 2): **до** правки эталона исполнитель такого заказа делает затронутые детали независимыми в своей сборке (§4.8). После правки это будет невозможно без восстановления из `_Версии`.
5. **Сохранение прежней ревизии.** Предупредить конструкторов, что эталон меняется, и убедиться, что файлы никем не открыты (контекстное меню «Кто открыл»). Для каждого изменяемого чертежа: открыть чертёж → Файл → Pack and Go → ☑ «Сохранить в одну папку» → папка `<изделие>\_Версии\Изм<N-1>\` → «Сохранить». Копия модели и чертежа прежней ревизии открывается независимо от эталона.
6. **Внесение изменений** в модели, чертежи и связанные документы (§6.1, п. 4). При новом обозначении: создать новое исполнение или документ по §4.2; старое не трогать.
7. **Ревизия** по §6.3: таблица изменений, файлы `_ИзмN`, прежние — в `02_PDF\_Аннулировано\` и `03_ЧПУ\_Аннулировано\`.
8. **Технолог:** поправить техкарту эталона, если изменились нормы; дать указание о заделе — что делать с деталями на складе и в цеху.
9. **Извещение.** Заполнить `ИИ-КТО-2026-NNN.xlsx` по шаблону (§6.7), подписи «Составил» и «Нормоконтроль» обязательны, «Утвердил» — Начальник КТО. Сохранить подписанный PDF в `02_БАЗА\_Извещения\`. В книге регистрации статус «Утверждено».
10. **Внедрение.** Разослать ИИ: мастерам, технологу, ОМТС, исполнителям затронутых заказов. Обновить файлы в `04_ПРОИЗВОДСТВО` у затронутых заказов, которые ещё не изготовлены. Строка в `История_изменений.xlsx` изделия. В книге регистрации статус «Внедрено».
11. **Снять временный доступ** (§2.8, процедура Б).

### 6.6. Какие заказы затрагивает изменение эталона

- **Открытые заказы** собирают детали эталона по ссылке на `Z:\02_БАЗА` и при следующем открытии покажут изменённую деталь. Для взаимозаменяемого исправления это и нужно. Если заказу нужна прежняя ревизия — шаг 4 §6.5.
- **Закрытые заказы** в `Y:\` хранят собственный комплект Pack and Go (§3.2, шаг 8); изменение эталона их не затрагивает. Заказы в `_Сдано` без комплекта (закрытые до версии 2.2) при открытии покажут новую ревизию; для них достоверны только PDF в архиве.
- **Поиск затронутых заказов** (до выполнения Д-59 — вручную, Начальник КТО): в `Разметка_СЗ.xlsx` каждого открытого заказа в `03_ЗАКАЗЫ` найти строки, где `Шифр` или `Эталон` равен шифру изменяемого эталона. Итог — список заказов в решении шага 2 §6.5.
- **Другие эталоны**, в которые входит изменяемая деталь: куратор открывает сборки эталонов раздела и проверяет «Файл → Найти ссылки».

### 6.7. Формы

Шаблоны лежат в `Z:\00_ИНСТРУМЕНТЫ\Шаблоны_изменений\` и `Шаблоны_заказа\` (Д-58).

**Извещение об изменении `ИИ-КТО-ГГГГ-NNN.xlsx`** — упрощённая электронная форма по приложению Б ГОСТ 2.503:

| Поле | Содержание |
| :--- | :--- |
| Обозначение ИИ, дата выпуска | `ИИ-КТО-2026-004`, дата |
| Изделие | шифр и наименование эталона |
| Изменяемые документы | обозначение каждого документа, ревизия было → стало (`Изм0` → `Изм1`) |
| Причина и код причины | текст и код по таблице Б.1 ГОСТ 2.503: 1 — конструктивное улучшение, 2 — технологическое, 3 — унификация, 4 — изменение стандартов и ТУ, 5 — по результатам испытаний, 7 — устранение ошибок, 8 — улучшение качества, 9 — требование заказчика, 16 — изменение норм расхода |
| Взаимозаменяемость | «сохраняется» или «нарушена — новое обозначение …» (§6.2) |
| Указание о заделе | что делать с изготовленными деталями: использовать, доработать (как), в брак |
| Указание о внедрении | с какого заказа или даты действует изменение |
| Применяемость | затронутые эталоны и открытые заказы (§6.6) |
| Разослать | мастера участков, технолог, ОМТС, исполнители заказов |
| Содержание изменения | было → стало по каждому документу, при необходимости скриншоты |
| Составил, Нормоконтроль, Утвердил | должность, фамилия, подпись, дата |
| Изменения внёс | фамилия, дата внесения |

**Книга регистрации ИИ** `02_БАЗА\_Извещения\Книга_регистрации_ИИ.xlsx`:

- лист «Извещения»: № п/п, обозначение ИИ, дата, шифр изделия, код причины, кратко, составил, статус (Проект / Утверждено / Внедрено / Аннулировано), ссылка на PDF;
- лист «Предложения»: дата, инициатор, шифр изделия, документ, описание дефекта, решение Начальника КТО, обозначение ИИ.

**История изменений изделия** `<изделие>\История_изменений.xlsx` (по смыслу — лист регистрации изменений, приложение В ГОСТ 2.503): Изм., дата, обозначение ИИ, документы изменённые / заменённые / новые / аннулированные, кратко, кто внёс.

**Журнал изменений заказа** `<заказ>\Журнал_изменений.xlsx` (форма 3, приложение Г ГОСТ 2.503), лист «Изменения»: № записи (`Ж-250-АСТ-3`), дата записи, обозначение документа, содержание изменения и указание о заделе, должность, фамилия и дата (исполнитель; отметка Начальника КТО при согласовании), отметка о внесении в подлинники, отметка о внесении в копии (`04_ПРОИЗВОДСТВО`, цех), примечание, статус. Замечания приёмки ведутся в задаче Битрикс24 (§3.2, шаг 5).

### 6.8. Памятка конструктору

| Ситуация | Что сделать | Где записать |
| :--- | :--- | :--- |
| Ошибка в своём заказе, документы ещё не выданы | исправить | нигде |
| Ошибка в своём заказе, документы уже в `04_ПРОИЗВОДСТВО` | §6.4 | журнал изменений заказа |

## ПРИЛОЖЕНИЕ А. Скрипт `New-OrderFolder.ps1`

Хранится в `Z:\00_ИНСТРУМЕНТЫ\Шаблоны_заказа\`. Создаёт дерево заказа и изделия по §1.2, копирует шаблоны, проверяет длину пути. Повторный запуск безопасен (существующие папки не трогает).

```powershell
<#
.SYNOPSIS  Создаёт каноническую папку заказа КТО и (при -Product) папку изделия по направлению.
.EXAMPLE   .\New-OrderFolder.ps1 -Number 250-АСТ -Object Школа12
.EXAMPLE   .\New-OrderFolder.ps1 -Number 250-АСТ -Object Школа12 -Product "И01_Стол_L1400" -Designation "250-АСТ-Т01.00" -Direction Металл
.EXAMPLE   .\New-OrderFolder.ps1 -Number 250-АСТ -Object Школа12 -Product "И02_Шкаф_ШГ800" -Designation "250-АСТ-Ш02.00" -Direction Корпус
#>
param(
    [Parameter(Mandatory)] [string] $Number,        # номер заказа, например 250-АСТ
    [Parameter(Mandatory)] [string] $Object,        # объект, например Школа12
    [string] $Product,                              # папка изделия: И01_Стол_L1400
    [string] $Designation,                          # обозначение изделия: 250-АСТ-Т01.00
    [ValidateSet("Металл", "Корпус")] [string] $Direction = "Металл",   # изделие КОМБИ — отдельный запуск для каждого направления
    [string] $Root = "Z:\03_ЗАКАЗЫ",
    [string] $Templates = "Z:\00_ИНСТРУМЕНТЫ\Шаблоны_заказа",
    [int]    $MaxPath = 200
)
$ErrorActionPreference = "Stop"
foreach ($s in @($Number, $Object, $Product)) {
    if ($s -and ($s -match '[\s\.]')) { throw "Имя «$s» содержит пробел или точку — запрещено §1.2." }
}
$order = Join-Path $Root "${Number}_${Object}"
foreach ($d in @("00_Исходные", "01_Корпус", "02_Металл")) { New-Item -ItemType Directory -Force -Path (Join-Path $order $d) | Out-Null }
foreach ($t in @("Разметка_СЗ.xlsx", "Журнал_изменений.xlsx")) {
    $dst = Join-Path $order $t
    if (-not (Test-Path $dst)) { Copy-Item (Join-Path $Templates $t) $dst }
}
Write-Host "[OK] Заказ: $order"

function New-ProductFolder([string]$section, [string[]]$subdirs, [bool]$withCard) {
    $prod = Join-Path (Join-Path $order $section) $Product
    foreach ($d in $subdirs) { New-Item -ItemType Directory -Force -Path (Join-Path $prod $d) | Out-Null }
    if ($withCard) {
        $card = Join-Path $prod "Техкарта_${Designation}_на_1шт.xlsx"
        if (-not (Test-Path $card)) { Copy-Item (Join-Path $Templates "Техкарта_на_1шт.xlsx") $card }
    }
    # запас на имя файла (обозначение + наименование + расширение) ≈ 60 символов
    $longest = (Join-Path $prod $subdirs[-1]).Length + 60
    if ($longest -gt $MaxPath) { Write-Warning "Полный путь к файлам достигнет $longest символов (> $MaxPath). Сократите имя изделия." }
    Write-Host "[OK] Изделие ($section): $prod"
}

if ($Product) {
    if (-not $Designation) { throw "Для изделия укажите -Designation (обозначение, например 250-АСТ-Т01.00)." }
    $metal  = @("01_3D", "01_3D\_Мастер", "02_PDF", "03_ЧПУ", "04_Тех", "_Аннулировано", "01_3D\Покупные")
    $korpus = @("01_bCAD", "02_PDF", "03_ЧПУ", "04_Тех", "_Аннулировано")
    switch ($Direction) {
        "Металл" { New-ProductFolder "02_Металл" $metal  $true }
        "Корпус" { New-ProductFolder "01_Корпус" $korpus $true }
    }
}
```

Требования к шаблонам в `Шаблоны_заказа\`: `Разметка_СЗ.xlsx` (лист «Позиции» по §5.1 с выпадающими списками `Стандартность`, `Направление`, `RAL`), `Журнал_изменений.xlsx` (лист «Изменения» по §6.7), `Техкарта_на_1шт.xlsx` (5 листов по §5.2).

## ПРИЛОЖЕНИЕ Г. Инструкции по ролям
