## 1. Резюме

Регламент хорошо структурирован (роли, папки, чек-листы, лист ознакомления) и решает реальную боль: 13 рабочих мест без PDM. Однако **несущая архитектура выбрана против рекомендаций вендора**: реселлеры Dassault называют плохой практикой синхронизирующие клиенты класса Dropbox/OneDrive/Synology Drive (рассинхрон ссылок, порча файла при сохранении, ложные «Файл не найден»). Регламент делает обязательным именно этот путь (`D:\CAD_WORKSPACE\` через Synology Drive, `РЕГ:246`).

> **Уточнение 13.09.2026.** В первой редакции аудита было сказано, что SolidWorks официально поддерживает работу с сетевого диска. Это неверно: GoEngineer пишет, что прямое редактирование файлов на сервере поддерживается не полностью, а GSC называет сохранение по сети самой частой причиной порчи файлов. Без PDM оба пути несут риск: синхронизация ломает блокировки и ссылки, прямой SMB рискует порчей при обрыве сети. Регламент v2.1 выбирает прямой SMB с защитой от порчи (§2.7, §4.11) и делает PDM Standard целевой архитектурой с порогами перехода.

## 2. Критические находки

### К-1. Local-First через Synology Drive — неподдерживаемая вендором схема (`РЕГ:246-248`)

**Факт.** GoEngineer (реселлер Dassault): использование «non-CAD-aware» синхронизаторов с SOLIDWORKS «не только не рекомендуется, но и считается плохой практикой». Типовые последствия: сервис синхронизации захватывает файл в момент записи → повреждение файла без возможности восстановления; ложные «файл не найден»; непредсказуемые падения. MLC CAD: «отключайте синхронизацию на время работы».
**Почему это относится к Synology Drive.** Клиент Synology Drive — такой же файловый синхронизатор (обход дерева, копирование по факту записи, конфликт-копии). Ни один механизм SW не знает о нём.
**Что теряется относительно `Z:\`.** Регламент сам это признаёт в `РЕГ:176-177`: на локальных копиях «мгновенного сигнала между ПК нет». То есть галочка Multi-User (`РЕГ:157`) на `D:\` проверяет только *локальные* дескрипторы, реальной блокировки между 13 ПК нет.
**Оценка предпосылки «Z: лагает» (`РЕГ:247`).** Не подтверждена измерениями. На гигабитной LAN с 13 пользователями типовые причины «лагов» SW по SMB: антивирус на сетевых путях, SMB signing/encryption, отсутствие SSD-кэша на NAS, один 1 GbE порт. Это устраняется дешевле, чем поддержка sync-архитектуры.

**Рекомендация.** См. раздел 6 (целевые архитектуры А/Б). Если Local-First сохраняется — обязательные меры из варианта В.

### К-2. Маска `*.swp` в чёрном списке выкидывает из синхронизации макросы SWplus (`РЕГ:140`, `РЕГ:412`)

**Факт.** `.swp` — штатный формат макроса SOLIDWORKS (VBA-проект). Макросы SWplus, на которых построен раздел 4.4, — это именно `.swp`: `MProp.swp` (`06_Документация/_Архив/ГЛУБОКИЙ_АУДИТ_КОДА_МАКРОСОВ_SWPLUS.md:70`, `06_Документация/_Архив/ВЕРИФИКАЦИЯ_МАТЕРИАЛОВ_И_ДРОБИ_ГОСТ.md:55`). Описание в `РЕГ:140` («сессионные файлы макросов») неверно: сессионных `.swp` у SW нет.
**Последствие.** Если макросы раздаются через синхронизируемую библиотеку, они не попадут на ПК конструкторов; при обновлении версии — у всех останутся старые.
**Рекомендация.** Убрать `*.swp` из фильтра. Хранить макросы в отдельной папке библиотеки (`00_БИБЛИОТЕКА\09_Макросы\`) или раздавать установщиком инструментария ЕСКД.

### К-3. Чек-лист 6.1 внутренне противоречив: фильтры (п.1) и On-Demand Sync (п.2) взаимоисключающие (`РЕГ:412-413`)

**Факт.** База знаний Synology: On-Demand Sync «не поддерживает фильтрацию файлов по размеру, имени или расширению». Включив On-Demand, вы теряете весь чёрный список из 2.2.
**Дополнительно.** On-Demand хранит на диске плейсхолдеры (Cloud Files API); SW при открытии сборки, `Pack and Go` и проверке read-only-файлов инициирует массовую подкачку — это прямо противоречит цели «сверхскорость на NVMe» (`РЕГ:246`).
**Рекомендация.** On-Demand Sync для CAD-папок **отключить**; синхронизировать библиотеку и текущие заказы целиком.

### К-4. «Заморозка» и «принцип одного хозяина» через ACL не защищают локальные копии (`РЕГ:177-179`, `РЕГ:223`)

**Факт.** Synology: пользователь с правом «только чтение» на Team Folder может создать **только download-only** задачу; локальные изменения на сервер не уходят «by design». Локальные файлы на `D:\` при этом остаются обычными записываемыми NTFS-файлами.
**Последствия.**
1. Конструктор с правом чтения открывает деталь из чужого заказа — SW открывает её **на запись** (замка нет, `РЕГ:158` не сработает), сохраняет, видит «зелёную галочку» — а на сервер ничего не уходит. Утверждение `РЕГ:177` «статус "Только чтение" берётся из ACL Synology» **не соответствует поведению клиента**.
2. После «заморозки» (`РЕГ:223`) у исполнителя остаётся полная локальная копия; дальнейшие правки молча не синхронизируются — данные расходятся без сигнала.
3. Как ведёт себя существующая двусторонняя задача при отзыве права записи — регламент не описывает; клиент уходит в ошибки.
**Рекомендация.** Заморозку делать **переносом заказа в отдельную общую папку `04_АРХИВ`** (не подключённую к клиентам конструкторов; на DSM 7.2 — WriteOnce/неизменяемые снимки), с обязательным удалением локальной копии у исполнителя. Права выдавать через группы DSM, а не правкой ACL в Проводнике по каждой папке (`РЕГ:217`).

### К-5. Резервное копирование отсутствует как класс (`РЕГ:127`)

**Факт.** В регламенте единственная защита данных — версионирование Synology Drive (8–16 версий; технически до 32). Это **не бэкап**: хранится на том же NAS, пофайлово, откат сборки из 100 файлов на «вчера» невозможен согласованно. Заголовок «Версионирование Btrfs» (`РЕГ:127`) смешивает два разных механизма (Drive versioning ≠ Btrfs snapshot).
**Рекомендация (стандарт 3-2-1).**
- Snapshot Replication: снимки общих папок КТО каждый час, хранение 7 дней; ежедневные — 30 дней; включить *Immutable snapshots* (DSM 7.2, Btrfs).
- Hyper Backup на внешний USB/второй NAS/облако ежедневно; проверка восстановления раз в квартал (записать в чек-лист сисадмина).
- UPS с корректным выключением NAS; RAID — указать уровень.

### К-6. Шаг 4 Начальника КТО (перенос новой фурнитуры в библиотеку и удаление локальной копии) рвёт ссылки сборки (`РЕГ:221`, `РЕГ:319`)

**Факт.** SW хранит абсолютный путь и ищет компонент по маршруту из 2.5. Перенос файла средствами Проводника + удаление копии = «Не удаётся найти деталь» у всех, кто открывает эту сборку (GoEngineer: перемещение/переименование только через Pack and Go/SW File Utilities).
**Рекомендация.** Перенос делать через *SOLIDWORKS File Utilities → Move* или «Replace» в сборке с последующим сохранением сборки исполнителем; либо оставлять локальную копию до сдачи и заменять ссылку в момент приёмки.

## 5. Пробелы (чего в регламенте нет)

1. **Единая версия SOLIDWORKS/SP на всех 13 местах.** Файл, сохранённый в более новой версии, не открывается в старой; при sync-архитектуре это происходит молча. Нужен пункт «версия/SP фиксируется приказом, обновление одновременно».
2. **Шаблоны документов** (`.prtdot/.asmdot/.drwdot`, `.slddrt`) и их расположение в библиотеке — в инструментарии ЕСКД они есть, в регламенте — нет.
3. **Управление изменениями по ГОСТ 2.503.** Папка `_Аннулировано_Старые_версии` (`РЕГ:373`) не заменяет извещение, индекс изменения и журнал. Без PDM минимум: суффикс ревизии в имени файла, `Журнал_изменений.xlsx` в заказе.
4. **Нормоконтроль (ГОСТ 2.111)** заявлен в аудитории (`РЕГ:10`), но в маршруте 3.2 его шага нет.
5. **Безопасность DSM:** 2FA, отключение учётки `admin`, SMB ≥ 2 (SMB1 off), брандмауэр, регламент увольнения/приёма (13 учёток), политика паролей.
6. **Сетевая адресация:** жёсткий IP `192.168.1.100` (`РЕГ:126`) вместо DNS-имени и DHCP-резервирования; смена адреса ломает `Z:`.
7. **Длина пути.** `D:\CAD_WORKSPACE\01_ЗАЯВКИ_В_РАБОТЕ\250-АСТ_Школа12\02_Металл\Изделие_02_Стеллаж_металлический_H2000\01_3D_Модели\Стандартные_изделия\<файл>` ≈ 185 символов; лимит Windows 260, у SW проблемы уже от ~250 (Pack and Go в подпапку). Нужны короткие имена папок.
8. **Процедура при конфликт-копиях Synology** (`filename (conflict …)`) — кто и как разбирает.
9. **Схема данных 5-листовой техкарты** (колонки, единицы, ключи) — без неё «AI-агент» (5.2) не может быть детерминированным; нет ответственного за проверку результата и ответственности за передачу данных в 1С.
10. **Периодичность пересмотра регламента и владелец** документа.

## 6. Пути оптимизации

### 6.1. Целевая архитектура (выбрать одну)

| Вариант | Для кого | Что даёт | Стоимость / риск |
| :--- | :--- | :--- | :--- |
| **А. SOLIDWORKS PDM Standard** (рекомендуется) | Если лицензии SW Professional/Premium — PDM Standard уже включён | Локальный кэш на каждом ПК (тот же Local-First, но CAD-aware); check-out/check-in = настоящие блокировки; версии по всем файлам согласованно; переименование/перенос без обрыва ссылок; состояния «В работе → Проверка → Утверждено → Архив» вместо ручных ACL; поиск по свойствам (обозначение, материал) | Нужна Windows-машина с SQL Server Express (бесплатно) — можно ВМ в Synology VMM или любой ПК; 1–2 недели внедрения; обучение |
| **Б. Прямой SMB `Z:` + снимки** | Если лицензии Standard | Одна копия и штатные блокировки; риск порчи при обрыве сети во время сохранения закрывается мерами §2.7 регламента v2.1; Multi-User и «замки» работают по-настоящему (то, что описано в `РЕГ:174-175`); одна копия данных; снимки Btrfs дают согласованный откат | Нужно измерить: время открытия самой тяжёлой сборки с `Z:` и с `D:`; при лаге — SSD-кэш, 2.5/10 GbE порт NAS, исключение сетевых путей из антивируса, отключение SMB signing внутри LAN |
| **В. Оставить Local-First (Synology Drive)** | Только как временный этап | — | Минимальный набор мер обязателен: единый корень `D:\CAD_WORKSPACE\` на всех ПК (никакого `Z:` в File Locations), On-Demand OFF, фильтр без `*.swp`, папки Auto-recover **и** Backup вне синхронизации, заморозка = перенос в архив, снимки + Hyper Backup, единая версия SW, регламент конфликт-копий |

Synology Drive во всех вариантах остаётся уместным для **читателей**: цех, снабжение, 1С — им нужны PDF/DXF/XLSX из `03_Производство`, не модели.

### 6.2. Моделирование (раздел 4)

1. **Вместо запрета Weldment (`РЕГ:274-278`) — Weldment + Save Bodies как исключение (уточнено 13.09: производные детали зависят от мастера и не заимствуются по одной, поэтому основной способ — скелет и независимые детали).** Каркас моделируется одной сварной деталью (параметрично, быстро), затем *Save Bodies* с опциями «Derive resulting parts from similar bodies» и «копировать свойства списка вырезов» даёт отдельные `.sldprt` на каждую трубу с живой связью с родителем. Требование «подетально в цех» выполняется автоматически, без ручного построения 30 труб.
2. **Семейства типоразмеров — конфигурации и групповые чертежи (ГОСТ 2.113), а не Make Independent на каждый заказ.** Стол L1200/1400/1600 — одна сборка с таблицей параметров и исполнениями `-01/-02`; заказ ссылается на исполнение. Make Independent (`РЕГ:323-357`) оставить для действительно уникальных доработок.
3. **Make Independent — дополнить, а не заменять (уточнено 13.09 по замечанию владельца).** Выборочный Pack and Go требует заранее знать все изменяемые детали, а в работе это неизвестно: изменение одной детали тянет соседние. Основной путь — копия только сборки и «Сделать независимым» по мере необходимости. Эталон только для чтения не даёт по ошибке сохранить изменённую эталонную деталь. Слабое место команды — чертёж не копируется (codestack, GoEngineer). Оно закрывается штатно: «Сохранить как» эталонного чертежа и «Заменить модель» на новую деталь (справка SOLIDWORKS, Javelin), а автоматически — макросом по образцу codestack. Перечень выпускаемых деталей получается в конце работы по «Ссылкам…». Pack and Go остаётся для случаев, когда состав изменений известен заранее целиком.
4. **Материалы:** краски RAL вынести из `.sldmat` в свойство «Покрытие»; фиксировать в регламенте, что графа 3 берётся из библиотеки ЕСКД (решение 13.09.2026), а MProp не переопределяет её.
5. **Скелет / компоновочный эскиз** для сборок «сверху вниз» — добавить как рекомендуемую практику для каркасов.

### 6.3. Выдача в производство (раздел 4.8)

- Труборез: **формат по ПО и версии конкретного станка** (таблица «Матрица форматов ЧПУ»); по умолчанию IGS с осью трубы вдоль X/Y/Z, SAT и STEP — после пробного импорта; для наклонных труб — система координат вдоль оси при экспорте.
- Лист: экспорт разверток командой *Export Flat Pattern to DXF* из модели (не из чертежа), линии сгиба — отключить или отдельный слой, сплайны → полилинии если требует CypNest, единицы мм, 1:1, версия DXF R2000/R14 ASCII.
- Имя файла ЧПУ должно нести толщину, марку и количество на изделие: `250-АСТ-Т01.10.01_S3_Ст3сп_x2.dxf` — иначе раскройщик заполняет вручную.
- Ревизия в имени PDF/DXF (`…_Изм1`), выпуск новой ревизии = извещение + запись в журнале.

### 6.4. Комплексный документ и «AI-агент» (часть 5)

1. **Структурированный вход вместо размеченного PDF.** Разметка СЗ Начальником КТО — таблица `Разметка_СЗ.xlsx` (позиция, тип `СТД/МОДИФИКАЦИЯ/КОРПУС`, шифр базы, тираж, RAL). PDF с пометками остаётся как первичный документ, но не как источник для программы.
2. **Детерминированный скрипт, а не LLM-агент**, для умножения норм и сведения по 5 цехам: Python + openpyxl по фиксированной схеме листов; запуск по расписанию (Container Manager на NAS или Планировщик Windows), журнал запусков. LLM допустим только на шаге «извлечь позиции из СЗ в таблицу» с обязательным подтверждением человеком.
3. **Google Antigravity** — IDE для разработчика, не среда исполнения производственного процесса; в регламенте инструмент должен быть заменён на скрипт с владельцем и версией.
4. **Данные СЗ (заказчик, цены, объёмы) не должны уходить во внешний LLM** без соглашения о необработке; предпочесть локальную модель или корпоративный API.
5. Источник норм — свойства моделей (материал, масса, длина, площадь окраски) через API SW / инструментарий ЕСКД, а не ручное заполнение техкарты конструктором; ответственность за техкарту — технолог (ЕСТД, ГОСТ 3.1118), утверждение — Начальник КТО.

### 6.5. Организация и администрирование (части 2–3)

- Права — через **группы DSM** (`KTO_Metall_RW`, `KTO_ReadOnly`, `Production_RO`) и Team Folders, а не ACL на каждую папку из Проводника.
- Скелет папки заказа создавать **скриптом** (`New-OrderFolder.ps1`) из одного канонического дерева — снимает противоречия П-1…П-3.
- В 3.3 добавить четвёртый тест: открыть сборку с *Rebuild all* (Ctrl+Q) и проверить «Что неверно»; для чертежей — висячие размеры; при наличии — автоматическая проверка свойств инструментарием ЕСКД.
- В 2.2 добавить в исключения `Thumbs.db`, `desktop.ini`, `*.swj` (журнал `swxJRNL.swj`), убрать `*.swp`.
- В 2.3 добавить: *External References → «Search file locations for external references»* (иначе шаг 2 маршрута поиска не работает), *Backup/Recover → Backup folder = `C:\SW_Backup\`*, снять «Save backup files in the same location».

## 7. Что в регламенте сделано хорошо (сохранить)

- Разделение СТД/МОДИФИКАЦИЯ на входе (`РЕГ:56-63`) — верная идея повторного использования.
- Read-only библиотека и база стандартов (`РЕГ:72`, `РЕГ:89`).
- Auto-recover вне синхронизации (`РЕГ:164`) — верно, нужно лишь дополнить папкой Backup.
- Опции External References read-only (`РЕГ:161-162`) — соответствуют рекомендациям Hawk Ridge.
- Тест «References…» в диалоге открытия (`РЕГ:234`) — правильный и быстрый.
- Изоляция новой фурнитуры внутри проекта (`РЕГ:317-319`) — правильный принцип «капсулы», требует лишь корректного переноса (К-6).
- Чек-листы и лист ознакомления — хорошая форма внедрения.
